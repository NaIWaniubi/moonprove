# 设计与边界

这份文档解释 moonprove 为什么这样实现，以及它在哪里停下。README 讲怎么用，这里讲为什么这样是对的，以及哪里不完美。

## 1. 判决只有三种，中间那块空白是明确存在的

每条义务被否定后交给求解器：

```
assumptions  ∧  ¬conclusion
```

- **不可满足** → 原命题在域内对所有输入成立 → `proven`
- **可满足** → 那个模型就是反例 → `violated`
- **两者都不是** → `undecided`

第三种不是失败，是信息。一个只输出前两种的工具必然在第三种情况下撒谎——要么把"没见过反例"说成"证明"，要么把"证不出来"说成"有问题"。两者都会让使用者放弃这个工具。

实现上，"不可满足"和"可满足"来自**不同的代码路径**，这是可靠性论证的核心：

| 结论 | 来源 | 为什么可靠 |
|---|---|---|
| `Unsat` | 化简到 `False`、区间反驳、Fourier–Motzkin 消元 | 每一步都是保持含义的重写或等价变换；消元在有理数域上的矛盾必然也是整数域上的矛盾 |
| `Sat` | 边界搜索 / 枚举找到模型 | 模型返回前用 `eval_bool` 重新校验；伪造的模型会被拒绝 |
| `Unknown` | 以上都没结论 | 不伪装 |

**没有一条路径能从一个失败推出另一个结论。** 这是刻意的：搜索失败不能推出 Unsat，因为搜索不完备；消元无矛盾不能推出 Sat，因为整数问题的有理松弛可满足不代表整数解存在（`2x = 1` 就是例子）。

## 2. Fourier–Motzkin：为什么它是可靠的，以及它在哪里不够

消元的规则是标准的。对变量 `x`：

```
a·x + r ≤ 0      (a > 0, 下界)
b·x + s ≤ 0      (b < 0, 上界)
─────────────────────────────────
(-b)·r + a·s ≤ 0        x 消失了
```

两个乘数 `-b > 0` 和 `a > 0` 都是正的，所以两式相加是合法的线性组合，结论被原式蕴含。消完所有变量后如果得到 `0 ≤ k` 且 `k < 0`，原约束集不可满足。

**在有理数上不可满足，是可靠的（sound）**：每个整数解都是有理数解，所以整数域上的解集是有理数解集的子集；子集为空则原集为空。

**在有理数上可满足，是不完备的（incomplete）**：`2x = 1` 在有理数上有解 `x = 1/2`，在整数上无解。moonprove 在这种情况下**不会**说 Sat，而是落到搜索。

严格性的处理有一个易错点：`x ≤ y` 和 `y < x` 的组合必须得到**严格**的 `0 < 0` 才是矛盾。如果只在一侧是严格时才标严格，这类矛盾就永远发现不了。规则是：**任一侧严格即严格**。

### 一个曾被掩盖的 bug

消元时 `v2 - v3` 与 `v3 - v2` 合成后 `v3` 的系数抵消为 0，但键仍留在 coefficient map 里。而"这是常量约束"的判据是 `coeffs.is_empty()`。一个值为 0 的条目让 map 非空，于是矛盾永远看不见。

症状很具体：`x ≤ y ∧ y < x` 被判为可满足。所有单向的不等式测试都通过，只有**两个不等式互相矛盾**这种用例才暴露。修复是在 `add_linear` 里剪掉零系数。

这类 bug 的教训是：数据结构的不变量（"系数非零"）如果不写进注释和测试，就一定会被某个路径破坏，而破坏它的路径通常正是你没想到要测的那条。

## 3. 区间反驳：整数离散性的用武之地

纯实数消元判定不了 `x > 0 ∧ y > 0 ∧ x + y ≤ 0`——因为约束 `x + y ≤ 0` 里 `x` 的系数是正的（下界），`x > 0` 也是下界，两个下界之间没有可直接合成的对。消元会先消掉 `x`，把耦合毁掉，什么也得不到。

但整数上有更直接的办法：`x > 0` 给出 `x ≥ 1`，`y > 0` 给出 `y ≥ 1`，所以 `x + y ≥ 2`，与 `x + y ≤ 0` 矛盾。这条推理只用**区间**，不用消元。

实现：先把每条约束按"变量 vs 字面量"和"变量 vs 变量"收窄到区间，再对每条线性约束算它在盒上的最小值和最大值：

```
min = constant + Σ (coef > 0 ? coef·low : coef·high)
max = constant + Σ (coef > 0 ? coef·high : coef·low)
```

`min > 0` 就反驳 `≤ 0`，`max < 0` 就反驳 `≥ 0`，`0 ∉ [min, max]` 就反驳 `= 0`。

"变量 vs 变量"的收窄（`lo ≤ hi` 让 `lo` 的上界变成 `hi` 的上界）是精度上的关键一步。没有它，`lo ≤ hi ≤ 1000` 这条链不会把 `lo` 收到 `1000` 以内，于是 `(lo + hi) / 2` 是否能回绕就永远算不出来，中点边界也就永远证不出来。

## 4. 回绕：建模了，但域是收窄的

整数算术按声明的位宽回绕：`a + b` 被翻译成 `wrap(a + b, w)`。这不能省——省掉就会"证明" `x + 1 > x` 在 32 位下恒成立，而它在 `x = MAX` 时是假的。

但回绕的建模和域的收窄是一对矛盾：

- 要正确地判定 `x = MAX` 处的行为，域必须包含 `MAX`；
- 域的端点要参与算术（比如两倍的端点），而 `2^31` 在 Int 里放不下。

选择是：域收到 `2^30`，并把域**显式声明**在每份报告里。代价是 `x = MAX` 处的回绕落在域外，工具在那里不作承诺；收益是求解器自己的算术永远不会被它验证的东西搞坏。

有一个可移除的优化：`wrap(t, w)` 在 `t` 的区间已经完全落在 `[-2^(w-1), 2^(w-1))` 内时等于 `t`。这个重写让线性片段看得见 `x + y`（否则它只是一个 `Wrap` 结点）。它的正确性依赖区间判断，而区间判断依赖收窄——三者是一个链条，每一环都有测试。

## 5. 循环：归纳法的三个义务

符号执行不能展开无限循环。moonprove 走 Hoare 逻辑的经典路线，对每个 `while c invariant I`：

```
(1) 进入时：  assumptions              ⊨  I
(2) 保持：    assumptions ∧ I ∧ c      ⊨  I'        （执行一次循环体后）
(3) 退出：    I ∧ ¬c  可用
```

三条义务各自是独立的求解器查询，各有一个判决。这让报告能定位到"不变式进不去"还是"不变式保不住"——两者的修法完全不同。

**没有 `invariant` 的循环**得到 `bounded` 判决，且路径**以 `¬c` 继续**（保守方向：不假设循环做了什么）。这意味着循环后面的断言仍然会被检查，只是它必须自己站得住。这比"整段跳过"有用：`examples/07_loop_no_invariant.mbt` 里循环后的 `assert i >= 0` 依然被证明，因为那条断言不依赖循环。

**不终止的循环**不在逻辑范围内。三条义务都不涉及终止性：它们证明的是"如果循环退出，那么不变式成立"。这是部分正确性（partial correctness），不是完全正确性。文档里这么写，是因为把部分正确说成完全正确是这类工具最常见的过度宣称。

## 6. 路径敏感的代价与做法

引擎同时携带所有活路径。一个状态是：

```
(路径条件: Term 列表, 符号存储: name → Term, 循环深度)
```

分支就分叉，两条路径各自累积条件。这带来两个后果：

- **精度**：`if x > 5 { assert x > 4 }` 能证，因为第二个分支带着 `¬(x > 5)`。
- **代价**：`n` 个嵌套分支产生 `2^n` 条路径。这是为什么需要路径上限——当前版本没有上限，因为语料里的路径数很小（最大 7 条）。**这是已知的扩展性限制**，路径爆炸时会退化成慢，不是错。

`return` 必须终止路径。这个语义最初写错了：`return` 把状态放进了输出列表，于是同一分支里 `return` 之后的语句继续在该状态上执行。症状是 `if x < 0 { return ... }` 之后的断言会在 `x < 0` 的路径上被检查，产生假的反例。修复是 `return` 返回空列表，退出状态单独记录供 `ensure` 用。

## 7. 表达式到逻辑项：诚实地拒绝

翻译函数 `eval_expr` 的签名是 `→ Term?`。`None` 表示"超出逻辑"，调用方把该义务标为 `undecided`。

明确拒绝的构造：

| 构造 | 为什么拒绝 |
|---|---|
| `a * b`（两个符号值） | 需要非线性求解器；一个不完整的非线性求解器给出的"证明"不是证明 |
| `a / b`（符号除数） | 需要额外的 `b ≠ 0` 守卫，当前版本不生成 |
| `f(x)`（未知函数调用） | 效果未知；假定它有某个值就是在编造前提 |
| `len(a)` | 支持，但作为独立的 `Nat` 变量，不建模数组内容 |

除法为字面量是支持的，并且有一个保持含义的重写让它在比较中变成线性的：

```
t / k < c   ⟺   t < c·k          (整数 t，正 k)
t / k ≤ c   ⟺   t < (c+1)·k
t / k > c   ⟺   (c+1)·k ≤ t
t / k ≥ c   ⟺   c·k ≤ t
```

四个方向都成立，这依赖 floor 除法的整数性质。这个重写是中点边界能证出来的另一半原因。

## 8. 测试策略

四层，每层测它自己该负责的东西：

**求解器（31 个）** — 化简器的每条规则用 13×13 的暴力求值逐点对拍（`terms_agree`）。求解器与暴力枚举在 10 个查询上对照（`brute_force_sat`）。Fourier–Motzkin 单独测矛盾/非矛盾/超片段三类。

**驱动（16 个）** — 端到端：源码进，判决出。每个用例的判决都能手工验算。包括"该被推翻的必须被推翻"这类反面用例。

**语料（10 个）** — 每个文件头部的 `EXPECT` 行写明它应该有几种判决，`test/verify_corpus.sh` 逐个核对。这是防止"工具悄悄改变主意"的闸门。

**界面（1 个 e2e）** — headless Chrome 打开页面，读 DOM 里的计数和反例文本。检查的不是"能加载"，是"渲染出的数字对"。

没有测的：路径爆炸、超大函数、并发（工具是单线程的）。

## 9. 不做的事

- **不声称完全正确性**。循环义务只覆盖部分正确性。
- **不声称域外成立**。所有结论限定在声明的盒子里。
- **不近似未知构造**。超出片段就 `undecided`，不会用一个"合理的猜测"填上。
- **不做过程间分析**。函数调用是未知效果。
- **不检查类型**。类型标注对分析无影响，`nat` 除外。

每一条都对应代码里一处显式的分支，不是文档里的一句免责声明。这是这份实现最想守住的性质：**它的每句"没问题"都能追到一个具体的证明步骤，它的每句"不知道"都能追到一个具体的 `None`。**
