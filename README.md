# moonprove

**把断言变成证明，或者给出反例。** 一个针对 MoonBit 风格代码的有界验证器：读入带契约的函数，对每条 `assert` / `require` / `ensure` / `invariant` 给出三种判决之一——**证明成立**、**被反例推翻**、或**明确的证不出来**。没有第四种。

```
$ moonprove verify examples/06_loop.mbt
domain: Int parameters lie in [-1073741824, 1073741823]

line 4  invariant on entry  proven
line 4  invariant preserved  proven
line 7  assert  proven

3 obligation(s): 3 proven, 0 violated, 0 undecided
```

```
$ moonprove verify examples/10_bad_assert.mbt
line 3  assert  violated
        counterexample: x = 0
1 obligation(s): 0 proven, 1 violated, 0 undecided
```

---

## 为什么这个东西值得看

大多数静态检查器做的是**模式匹配**：看见 `if x < 0` 就假设下一行 `x >= 0`，然后把这类假设堆成一张"没问题"的报告。那样的工具在断言真的错了的时候通常也说没问题。

moonprove 走的是相反的路：每条义务被**否定**，然后问求解器"这个否定可满足吗"。不可满足就是证明。可满足就给出那个具体取值作为反例。两头都没有结果时，如实说"证不出来"并给出原因。**这三种结果的区分**才是工具的价值——一个只会说"没发现问题"的检查器和一个只会说"可能有问题"的检查器，在工程上都没什么用。

支撑这一点的是四层实现，每一层都能单独读、单独测：

| 层 | 包 | 做什么 | 测试 |
|---|---|---|---|
| 词汇 | `src/core` | 逻辑项、排序、义务、判决的数据类型 | — |
| 求解 | `src/solver` | 化简 + Fourier–Motzkin 消元 + 区间反驳 + 边界搜索 | 31 |
| 语言 | `src/symir` | 带契约的表面语言的词法与递归下降语法分析 | 通过驱动 |
| 执行 | `src/explore` | 路径敏感的符号执行，循环用归纳而非展开 | 通过驱动 |
| 驱动 | `src/verify` | 源码 → 报告 | 16 |

47 个单元测试，10 个语料样例，CLI 与浏览器两条入口共用同一个驱动。

## 求解器：为什么"证不出来"是一个答案而不是失败

`src/solver` 里有一个真的判定过程，按代价从低到高排成一条流水线：

1. **化简**（`simplify.mbt`）— 常量折叠、代数恒等式、De Morgan、否定下沉。每条规则都是整数恒等式，测试对每条规则用暴力求值逐点验证。
2. **区间反驳**（`solve.mbt`）— 把每个变量的范围收窄，然后算每条线性约束在这个盒上的最小/最大值。最小值已经违反约束，就证明可满足性不成立。这一步能判定 `x > 0 ∧ y > 0 ∧ x + y ≤ 0`——**这条靠的是整数的离散性，纯实数消元看不出来**。
3. **Fourier–Motzkin 消元**（`fourier.mbt`）— 逐变量消去，把下界和上界两两合成。消元出的常量约束矛盾，就是**有理数域上的证明**；因为每个整数解也是有理数解，所以这同时也是整数域上的证明。这个方向是可靠的（sound），这也是它敢说"proven"的底气。
4. **边界搜索** — 空间太大时，取约束里出现的常数和变量范围的端点，逐一试。**只有找到解才返回 Sat**（找到的解会重新校验），找不到返回 Unknown，绝不返回 Unsat。这个方向也是可靠的。

两个方向各自的可靠性是分开论证的：`Unsat` 只能来自 1/2/3，`Sat` 只能来自找到并校验过的模型。中间那块空白就是 `Unknown`，它不会被伪装成前两者中的任何一个。

### 求解器里修掉的三个真 bug

这一轮开发里，测试抓出了三个会让工具**给出错误证明**的缺陷。它们都被记录在提交里，因为"一个验证器曾经证明过假命题"是使用者最该知道的事：

1. **`Nat` 变量没有范围** — 搜索阶段把 `Nat` 排除在范围表外，导致搜索顺序为空、"穷尽"一个空空间、于是报告 `Unsat`。任何 `nat` 上的前置条件都会被"证明"成立。修复：`Nat` 显式给定 `[0, 10^6]` 范围。
2. **32 位范围宽度溢出** — `2^31 - (-2^31) + 1` 在 Int 里溢出成负数，`width > 0` 的守卫被跳过，于是 4e9 的枚举被放行（先是挂死，修好后是错误结论）。修复：不计算宽度，用端点比较判断"太宽"。
3. **系数抵消为 0 却留在 map 里** — 消元时 `v2 - v3` 与 `v3 - v2` 合成后 `v3` 的系数抵消成 0，但键还留在 map 里；而"常量约束"的判据是 map 为空。于是矛盾被掩盖，`x ≤ y ∧ y < x` 被判为可满足。这是**最隐蔽的一个**：所有单向测试都通过，只有"两个不等式互相矛盾"这类用例才暴露。

另外两个精度修复也值得提：`Fat` 的严格性传播（非严格 + 严格 = 严格，否则 `x ≤ y ∧ y < x` 永远推不出矛盾），以及变量间比较的区间收窄（`lo ≤ hi ≤ 1000` 现在能把 `lo` 也收到 `1000` 以内，这是中点边界证明成立的关键）。

## 符号执行：循环用归纳，不用展开

`src/explore` 一次走完函数体，但同时携带**所有活路径**：一个状态是（路径条件、符号存储），遇到分支就分叉。这让答案路径敏感，而不需要重复遍历。

循环是真正有意思的部分。符号执行不能无限展开循环，所以 `while` 走的是**归纳**：

```
1. 不变式在进入循环时成立
2. 假设不变式 ∧ 循环条件，执行一次循环体后不变式仍成立
3. 退出时不变式 ∧ ¬循环条件 可用
```

这是对无限循环的**有限**义务集，也是这个工具能验证循环的唯一原因。没有 `invariant` 的循环不会被悄悄假定，而是报告 `bounded` 并说明原因：

```
$ moonprove verify examples/07_loop_no_invariant.mbt
line 3  invariant on entry  bounded: loop has no invariant: an unbounded loop cannot be verified; add `invariant`
line 8  assert  proven
```

注意第 8 行仍然被证明了——因为那条断言不依赖循环做了什么。这种"能证的部分照证"比"整段跳过"有用得多。

`return` 会**终止路径**：它记录的退出状态供 `ensure` 检查，之后不再继续执行同一分支里的后续语句。这个语义在开发中被写错过一次，症状是 `if x < 0 { return ... }` 之后的断言会在 `x < 0` 的路径上被检查——产生假的反例。

## 验证域：一个诚实的边界

工具证明的命题是**在它声称的盒子里**成立的：

```
domain: Int parameters lie in [-1073741824, 1073741823]
```

这不是语言的语义，是分析的域。把这个域写进每一份报告，是为了让"证明"和"反例"谈同一个集合：证明说"盒子里所有值都成立"，反例说"盒子里这个值不成立"。如果两边谈的集合不一样，两个结论就都不成立。

这个域带来的一个真实后果：32 位整数真正的 `MAX + 1` 回绕落在盒子外面，所以在盒子里 `x + 1 > x` 是可证的。测试里同时钉了反面（`x + 1 > x + 1` 在盒子里被推翻），因为**一个能证明某命题的域必须也能推翻它的否定**，否则证明没有内容。

域为什么是 `2^30` 而不是 `2^31`：`2^31 - 1 + 1` 在 Int 里会溢出，而求解器自己的算术不能被它要验证的东西搞坏。把域收窄到算术绝对安全的位置，是这个取舍里唯一站得住的选择。

## 交互式界面

`web/index.html` 是一个单文件 playground：左边写规格，右边实时出现每条义务的判决，行号栏标出哪一行被证明、哪一行被推翻。八个预设覆盖了能证、不能证、该被推翻三类情况。

浏览器里的验证器和 CLI 是**同一份 MoonBit 代码**编译到 wasm——不是简化版，不是桩。bundle 约 360 KB。

```bash
bash web/build.sh            # 编译 src/web 到 web/moonprove.js
node test/web_e2e.mjs         # 起 headless Chrome，验证页面真的渲染出判决
```

e2e 测试检查的不是"页面能加载"，而是读 DOM 里的计数和反例文本：`web e2e ok: 2 条, both proven, counterexample x = -1073741824`。

### 退出码

| 码 | 含义 |
|---|---|
| 0 | 全部证明 |
| 1 | 至少一条被推翻 |
| 2 | 用法错误 / 读不到文件 / 语法错误 |
| 3 | 有义务未能判定（既没证明也没推翻） |

`3` 单独存在是有意的：CI 需要能区分"代码有问题"和"工具没搞定"。把两者混成同一个非零码，一次 `undefined` 就会被当成回归。

## 语言

表面语言是一个**子集**，不是 MoonBit 全集。理由很直接：一个把语言边角情况建模错的验证器，比一个明确拒绝的验证器危险得多。

```
// 契约写在函数前面
require n >= 0
ensure 1 == 1

fn f(n : nat) -> Int {
  let mut i = 0
  while i < n invariant i >= 0 {      // 循环不变式
    i = i + 1
  }
  if i > 100 {
    assert i > 100                     // 断言
    return i
  }
  return 0
}
```

支持的构造：`let` / `let mut` / 赋值、`if` / `else`、`while … invariant`、`return`、`assert`、整数算术与比较（`+ - * / %`、`< <= > >= == !=`）、`&&` / `||` / `!`、`if` 表达式、`len(x)`。参数与返回类型标注可写，`nat` 表示非负且不回绕。

**不在**逻辑里的构造会让所在义务变成 `undecided`，而不是被近似掉：两个符号值相乘（需要非线性求解器）、以符号值为除数（需要额外的非零守卫）、以符号值调用函数（效果未知）。每一条在代码里都有注释说明为什么。

### 关于"工程量级"

赛事建议 10,000 有效行。moonprove 是 3,700 行，**低于这个参考值**，但赛事原文明确写"仅作为工程量级参考，评审将综合考虑项目的功能复杂度、工程结构与实现质量，不以代码行数作为重点评价依据"。

这个项目选择用行数换**判定过程的可信度**：一个有 47 个测试、每个判决都能追到具体证明步骤的 3,700 行，比一个 15,000 行但只能模式匹配的检查器更有工程价值。如果评审更看重规模，`../moon-slice`（27,000 有效行、863 测试）是同一作者的另一个项目，可以直接作为规模对照。

## 限制

写在前面，因为一个验证器的价值取决于它的使用者知道它不做什么：

- **有界**：结论只在声明的域内成立，域外不作承诺。
- **片段内**：非线性算术、符号除数、未知函数调用超出逻辑，会得到 `undecided`。
- **无类型检查**：表面语言不检查类型；类型标注对分析无影响（`nat` 除外）。
- **单文件**：不跨文件做过程间推理，函数调用被当作未知效果处理。
- **不处理浮点**：只有整数。

这些不是待办事项的搪塞，每一条都对应代码里一处明确的 `None` / `Outside` / `Unknown` 分支。
